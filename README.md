# rtw-map

A map-based planner for long, multi-country trips. It's built for cities worldwide; detailed data currently covers the Balkans, Central & Eastern Europe (incl. Austria), Poland, the Baltic States and Russia, plus Taiwan, Japan, Thailand, Vietnam, Malaysia, Singapore and Cambodia (more regions to follow).
You choose where and when, and how you like to travel. It suggests a route with nights per city, enforces the Schengen 90/180 rule,
checks visas and travel advisories, and shows weather, costs, health advice, mobile internet and transport for every stop.

See [PLAN.md](PLAN.md) for the product plan, decisions and roadmap.

## Run it

```bash
npm install
npm run data:pull   # the data lives in a private Cloudflare R2 bucket, not in git (see "Data storage")
npm run dev
```

Open the URL Vite prints (usually http://localhost:5173), pick dates and **+ Add regions or countries** on the Trip tab, sign in, then **Plan with AI**.

| Command | What it does |
|---|---|
| `npm run dev` | Dev server |
| `npm run dev:api` | The site's Worker locally (port 8787), for the trip assistant; `npm run dev` forwards `/api` to it. Needs `GEMINI_API_KEY` and `SESSION_SECRET` in `.env.local` (and `ADMIN_EMAILS` to edit assistant limits) |
| `npm run dev:runner` | The assistant's runner locally (port 8788), which answers messages about saved trips on the server; needs `RUNNER_URL` and `RUNNER_SECRET` in `.env.local` (without them the browser answers instead) |
| `npm run build:runner` | Bundles the runner, with the app's assistant code and data, for Cloud Run (`build/runner/`) |
| `npm test` | Planner and formatting tests (Vitest) |
| `npm run lint` | oxlint |
| `npm run build` | Type-check + production build into `dist/` (static files) |

## What it does

- **Trip assistant** (Assistant tab, needs **Sign in with Google**; at most $1 of Gemini use per account per day, priced from each call's tokens and shown as the percent used in a ring at the top right of the chat, amber near the limit, which a click opens with a bar and the time to the reset (a quick question costs about a cent, a long Plan with AI run much more); admins (the `ADMIN_EMAILS` secret) can give particular accounts, by email, another daily limit under **Assistant limits…** in the account menu (those users see e.g. "5× AI usage" under their name there, with a one-time notice when it's raised); account menu with Sign out at the top right): chat with Google Gemini to ask about or change the trip. **✨ Update with AI** beside the title of a card the assistant can fill in (a city's Where I stay; its Daily cost, Stay and Food & drink prices; the Phrases card; not the Trip tab's preferences, photos, links, notes or Today's cards, quicker done by hand) opens it with a question about that card and a short answer saying what to send (a booking, a receipt, a screenshot, a few words), with no model call until you reply. **Ask AI** in a city or journey panel's header opens it about that panel (beside it; on a phone, a sheet over it that goes back to the city when closed), with a question and a short answer saying what it can do there and up to four questions to click, the open tab's first (*What's the weather like in Athens during my trip?*, *Is 6 nights in Athens the right amount?*, *What's the best way from Athens to Thessaloniki?*; for a city not in the trip, whether to add it; for a journey, the ways to go), with no model call until you pick one or write your own. It uses the app's own actions and data (add/remove/move stops, reorder or reverse the whole route in one step, nights, dates and how flexible they are, regions and countries anywhere in the world, every preference, the trip's plans) and can look up anything in the app's data: any city in full, many cities side by side, and the route between any two cities. For a big what-if it makes a new plan first, so the current one is kept. Changes apply right away, and each reply that changed the trip can be undone. A message has no limit on its model calls: the assistant works until it answers (routes and cities can be looked up many at a time), and **■ Stop** (next to *Working on it…* and in place of Send) ends it after the call under way, keeping what it changed (undoable), with **Continue** to go on. Each reply shows how long it took and what it used (calls, tokens in and out, and the cost at Gemini's prices; a tooltip gives cached tokens), the reply under way counts up (its time too, from when it was asked), and the ring at the top of the chat opens the chat's total. **New chat** keeps the chat it replaces: **Chats** at the top of the tab opens a panel from the left with the trip's chats (over the whole app, as Settings is from the right: the open one, then the others, latest first, each titled by its first question with the date of its last), and a click opens one, the open one kept in its place. The last 30 are kept with each trip (on the server, so on every device); a chat you leave keeps what each reply changed, but no Undo. Long runs wait out the per-minute limit, older tool results are shortened, and a very long run drops its oldest steps (telling the model), so requests stay within the limits. **Context** chips above the message box show what's on screen (the open city and tab, an open journey, the map view); they're sent with the message so "here" and "this city" make sense, and any of them can be left out. When it asks you to choose or confirm, its reply ends with buttons to answer in one click (e.g. *Yes, swap them* / *Keep Kotor*); a stopped run offers **Continue**, and a failed reply **Try again** (sent in its place). **Attach** images and PDFs to a message (the paperclip, or paste or drop them on the message box; up to 4, 10 MB each), such as a booking confirmation, a ticket or a screenshot: they go to Gemini with that message only (Google deletes them within 48 hours), and the chat keeps their names (and a small preview of an image). Ask it to save a booking and it becomes a stay in My visit; give it prices you paid (a receipt, a menu, a booking) and it keeps them for that city's costs. Answers use your currency and °C/°F, in the language you write in, with headings, lists and tables. Your own choices stay yours: it changes the setup (regions, countries, dates, preferences, plans) or locks a stop only when you ask; while planning (Plan with AI, Update plan) those changes are refused and it suggests them instead, and nights it sets on its own are left unlocked when it's done. Optional "Think harder".
- **Plans**: a trip can have up to 8 plans, versions of the itinerary each with its own setup and preferences, shown as a bar under the left panel's tabs. **+ Plan** copies the current one to try something without losing it; the active plan's menu renames or deletes it; **Compare** shows them side by side (dates, stops, countries, cost, per day, travel time, Schengen days, problems, and the cities one has that the other doesn't). The trip's name and assistant chat are shared by its plans.
- **Trip** (the left panel's first tab): dates, each exact or flexible by up to ± 14 days (set with − / +) (the assistant picks the dates within them when it plans, so the trip is as long as its stops want rather than stretching or squeezing them; the dates planned show under the Trip tab's title, with the nights and stops), where to go (each country *must* / *optional* / *excluded*: a click goes optional → must → excluded; countries in a region start optional and every region gets at least one stop, a country added on its own starts as must or optional as chosen when adding it, and "do not travel" countries start excluded; in no particular order, the assistant picking the route, unless **In this order** is ticked; each region's card folds to a line counting its must, optional and excluded countries, and opening one folds the others), the days to spend in each region, all its countries told, and in each country (a fewest and a most, either left empty for any; the assistant plans within them, after the Schengen limit, and Checks says when the trip has no room for them), number of stops (optional: a fewest and a most, either left empty for any; the assistant plans within it, and Checks says when the trip doesn't), Schengen days already used, and free-text wishes. **+ Add regions or countries** picks from the whole world, regions or single countries (any number, ticked in a searchable list or clicked on the map): 29 regions as travellers use them (Balkans, Nordic countries, Caucasus, Central America…), each country in one; every country has at least its capital, with curated data (see "Capitals from open data" below); a country with only open data (one added to the map later) can be added, but is marked "not in plans yet" and left out of the plan (Checks says so) until it has curated cities. While the Trip tab is open the map shows the trip's countries (must visit strong, optional faint, excluded grey) instead of the route and stops; pointing at a region's card or one of its countries, or at a place in the **+ Add regions or countries** list, shades it in blue on the map and brings the region (or country) into view, zooming out to fit it but never in. Each part is its own card, the preferences follow them (below), and **Plan with AI** stays pinned to the bottom of the panel (once there's a plan it reads **Replan from scratch**, which asks first, saying whose stops it replaces, e.g. *It replaces Plan A's 12 stops*, and that the version history can bring them back, with **Replan a copy** to keep them: a copy of the plan, switched to, that the replan then fills; while something has changed since the plan, Review changes takes its place, below). Each plan remembers the setup and stops it was last made or updated from (by Plan with AI, Update plan, or any change the assistant made in the chat): when they've changed since (the setup: regions, dates, days, stops, preferences, wishes…; your own edits to the stops; nights that no longer add up to the dates), **Review changes · N** takes the place of **Replan from scratch** (and is pinned to the bottom of the Itinerary tab too): it lists what changed in a dialog, grouped under Dates, Places, Stops, Preferences and Plans (*Added region Balkans* under Places, *Kraków: 3 → 5 nights* and *2 nights over the dates* under Stops, *Pace: balanced → fast* under Preferences), with **✨ Update plan**, which, with *Make a new plan* ticked (*Plan the rest of the trip again* while travelling), makes a new plan instead, the current one kept in the version history (the Stops changes, your edits to the stops, are then struck through: a new plan doesn't keep them): the assistant, starting afresh, keeps the plan and your own edits and changes only what those changes call for. A finished plan or update (not a stopped one) clears the line. Plans are made with the assistant, so only signed in (signed out, the button says **Sign in to plan with AI** and opens the Assistant tab, where the sign-in is): each time a clean plan (*Plan my trip from scratch…*, with the wishes): the assistant, starting without the conversation so far, builds the itinerary itself for the setup, wishes, preferences and interests (it looks up the cities and routes, then puts in every stop with its nights in one step), and Undo goes back to the trip from before.
- **Preferences**, in the Trip tab under the trip's own cards: a folded card per topic (Who, Trip goals, Daily cost, Get around, Interests, Comfort), each with a line saying what's set; open one to change it (one at a time: opening another folds it) (saved with the trip; a new trip starts from the current one's): home city (any city the app knows; the trip starts there and, unless one way, returns there; not a stop: the itinerary shows the journey from home and back, the map draws it dashed, and the cost includes it; long flights aren't in the timetable data, so they're estimated from distance: ~800 km/h, one change above 7,000 km, a fare range by distance), passport, pace and interests; **daily cost**: a daily budget per person (optional), and the defaults for every city's daily cost, set like in a city's Costs tab: bed (dorm or private room), each meal (breakfast: DIY, local place or skip; lunch and dinner: DIY, local place, restaurant or skip; a DIY meal is supermarket food: breakfast 2 slices of bread, an egg and a banana; lunch or dinner 125 g pasta, 150 g chicken breast and 200 g tomatoes), café coffees and beers in a bar (0–2 a day), and the most you'd pay a night (a day of public transport is always counted; taxi rides are added per city); then travel between cities, overnight travel, longest travel day, your temperature bands (a slider coloured cold → hot with a handle where each of cool, pleasant, warm and hot starts, by default 12, 18, 28 and 32°C; dragged or moved with the arrow keys, in °C or °F; the map's Weather view, its legend and each city's weather use them), the months to avoid (cold or hot by your bands, rainy; none by default); and **trip goals**: what matters most (balanced, more countries, top highlights) and what to do about expensive places (nothing, shorter stays, skip where optional). The planner uses the trip goals, pace, interests, and the months you avoid (places whose highs are cold or hot by your bands, or rainy, in the months you'd be there, score lower) when it makes a plan, and Checks warns about cold and hot stops by the same bands (highs as they feel when temperatures are shown that way), whether or not you avoid them (rainy ones are a warning when you avoid rain, otherwise a note). Daily costs add up the bed, meals, drinks and getting around you chose; the rest is stored for later checks. Breakfast, lunch and dinner explain the chosen option with an ⓘ (a tooltip on hover or tap). The assistant can apply a travel style preset (Shoestring, Backpacker, Budget private, Mid-range, Comfort) that sets these in one go.
- **Generated plan**: picks cities, orders the route, assigns nights, keeps Schengen days ≤ 90 in any 180-day window, estimates cost as a range (shown at the top of the Itinerary tab, with an ⓘ on what it counts, and ~per day, under a line with the trip's dates, nights and stops, like the Trip tab's). Ground transport wins unless a flight clearly saves time: flights count ~2½ h of airport time and their fare.
- **Editing**: ± nights (locks that stop), lock, remove (asks first), drag to reorder, add a city from the map (where it fits the route, with its usual stay). Lock and remove show on pointing at a stop, and always on the open city's: a stop's city panel has **Make changes** beside its dates and nights (they then show in Review changes, below), which opens the Itinerary beside it (on a phone, its sheet over the city's) at that stop. An edit changes only what it touches: nothing re-fits the plan by itself. **Undo** and **Redo** in the top bar (on a phone, at the bottom of the Trip and Itinerary tabs, beside Review changes; and ⌘Z / ⇧⌘Z, Ctrl+Z / Ctrl+Y on Windows and Linux, anywhere but in a text box) step back and forth through the plan's edits, its stops and its setup in the Trip tab alike, by hand anywhere (quick clicks in a row count as one) and each of the assistant's replies as a whole, each saying for a few seconds at the top of the map what it did (*Undone: Kraków: 3 → 5 nights*); not while the assistant is working, and they start afresh on another plan or trip. Then **Review changes**, pinned to the bottom of the Itinerary tab, lists your edits with **✨ Update plan**, which has the assistant fit the rest around your edits (or ask it for the moves directly: after its changes it leaves the plan in order, the nights adding up to the dates).
- **Read-only**: the lock at the end of the plan bar makes the whole trip read-only (**Read-only** while on), so nothing in it changes by accident, by you or the assistant: the itinerary loses its ± nights, lock, remove and drag, the Trip tab's and a city's Daily cost controls are dimmed (cards still open, to read), Undo, Redo, Update plan, Plan with AI and adding or removing cities are gone, and plans can be switched and compared but not added, renamed or deleted. The assistant still answers, but its tools that change the trip are refused, so it suggests instead. Saved with the trip (on any device, and for the assistant's runs on the server); click it again to edit. Not while the assistant is working.
- **My visit**: a city's own tab (after Overview) for what you keep there: **stays** (the hotel, hostel or flat: name, address with a map link, check-in and check-out days, booking reference, price, booking link and a note such as the door code; a new one starts with the visit's dates), **photos** (album links, e.g. a Google Photos share link) and **links** (tours, tickets, restaurants; a link to a public post or video on Instagram, Threads, Facebook, X, TikTok or YouTube shows the post under it with **Show post**, loaded from that network only when tapped and only with a connection; a YouTube video shows its thumbnail, title and channel, and plays at half volume when the thumbnail is tapped), each changed in place with **Edit** and **Done** (saved as you type) or removed, and **My notes**. A journey has its own **tickets** in its panel (each flight, train, bus or ferry booked: carrier and number, when it leaves and arrives in each place's own time, from and to which airport, station or port, booking reference, price, link and a note such as the seat) and its notes. Prices you saw in the city (its Costs tab, below) and your own phrases (its Phrases tab) are kept here too. Notes are written in Markdown (headings, **bold**, lists, to-dos, links, tables) and shown formatted, with **Edit** (or a double click) to change them and **Done**; a to-do's box can be ticked right there. All kept for the trip per city, whichever plan is shown (a stay's dates tell two visits to a city apart), also while it's read-only, and private: only you see them (and the assistant, which reads them and, when you ask, adds or changes them, e.g. *save this booking*, each listed under its reply with **Undo**). In the itinerary a stop shows marks for its note, its stay (the name on hover) and its albums (each opens), a journey for its tickets (what they are on hover) and its note; the journal shows a stop's albums by its name. Like the journal, they're kept on the device first and merged item by item across devices (a stay added offline on the phone and an album added on the laptop are both kept).
- **Trip status**: a chip by the itinerary's dates says where today is against the trip: *Planning · starts in 59 days* before it, *Travelling · day 5 of 24 · Shkodër* during it (the end date, the day of leaving, is the last day) and *Finished* after it.
- **Today**: while the trip is under way, a **Today** tab appears after the Itinerary, and the app opens on it (on a phone, half open; a link or refresh naming a tab keeps that tab). It shows the day of the trip, tonight's city and night (*Night 2 of 3 · leaving tomorrow for Berat*), the journey of the day or the next one (mode, time, price, the timetable's tips and checks, the journey's tickets and note when there are, details and the links to check it elsewhere, as in the journey panel; from the day before, quick links to the arrival city's getting around, paying and SIM), **tonight's stay** (its address, booking and note, or a way to add it with the stop's dates), the forecast for today and tomorrow (tomorrow in the next city when you move on), today's journal entry, this stop's checks, the nights left here and in the trip and the Schengen days used so far (when the rule applies and the trip goes there).
- **Journal**: one entry per trip day: the day's highlight, a few lines and how it was (1–5 stars). Written on Today (*Today's entry*, or yesterday's when that isn't written yet), or any day so far in the Itinerary's **Journal** (beside **Stops** from the trip's first day: every day newest first, under the stop where its night was; a stop with days written shows how many, a click opens them). Saved on the device as it's typed, so a day written with no connection is never lost, and sent to the account when there's a connection (*Offline · saved on this device* until then). Kept apart from the plans, merged day by day on the server: days written on the phone and on the laptop are all kept, the latest edit of a day wins, and the assistant working on the trip doesn't touch it. Not in Undo; only you see it (never in a shared trip). Signed out, it's kept in the browser and goes with the trip into the account at sign-in.
- **Travelling**: while today is one of the trip's days, the stops already left are faded and today's is marked **Now**, in the itinerary (left stops' day circles grey), the timeline (grey in the Route view) and on the map (a pulsing halo on today's stop; in the Route view the stops left and the journeys made are grey and the next journey thicker). The days up to today are what happened: Plan with AI (**Replan from tomorrow**) and Update plan change only what comes after today, and the assistant's changes to those days are refused (tonight's stop can still get more nights, or fewer if it ends tomorrow or later). An edit by hand that changes them (a stop's nights or dates, removing or moving a stop, the start date) asks first.
- **Sharing**: **Share…** in the trip menu (signed in) makes a public link to the trip: anyone with it sees it read-only, without signing in (only the Itinerary tab, with the trip's dates, nights and stops, and every city and journey; not the Trip tab or the assistant). Your stays, albums, links and notes, your journal, your wishes for the assistant and the chat are never in it. The link always shows the trip as it is now; **Stop sharing** turns it off (it then says the trip isn't shared), and the trip list marks shared trips. Opening a link leaves your own trip in that browser as it was.
- **AI apps**: the assistant you already use (Claude, ChatGPT, Codex, Gemini CLI) can read and change your trips: **AI apps** in the account menu gives the server's address (`https://<site>/mcp`) to add as a custom connector, or the command for Claude Code, Codex or Gemini CLI. The first time, the app opens a page here to sign in with Google and allow it; it then reads your trips, the app's city data, your journal and My visit, and, if you leave **Also let it change your trips** ticked, changes trips and My visit with the same tools as the app's assistant: with its own Gmail connector, say, it can find your hotel and flight confirmations and save them as stays and tickets (*add my bookings for October to my trip*). Its changes appear in the app when you come back to it (checked every 15 seconds while it's in view), under a notice listing them with **Undo**; an edit made here meanwhile isn't saved over them. **AI apps** lists the apps you allowed (reading, or reading and changing), each with **Disconnect**. Its model use is on that app's own subscription, not the assistant's daily allowance. See "Other apps' assistants (MCP)" below.
- **Checks**: countries left out (no curated cities yet, or not admitted on the passport), Schengen, visas per passport, travel advisories (UK FCDO + US State Dept), Kosovo → Serbia border, weather, air pollution, tap water, cash-only places and countries where foreign cards fail, pace, limited English, unreachable or estimated legs, and where the plan doesn't fit your preferences: a stop over the daily budget or the most per night (amounts in your currency), an expensive place (when you'd skip those, or stay shorter and it's longer than usual), the trip over the budget on average, a travel day longer than the longest you'd like, or overnight when you'd rather not. A stop or journey with a problem or warning gets a mark in the itinerary (● or ▲, its checks on hover), and its city panel shows them where they belong (below); the list above the itinerary leaves out a stop's own problems and warnings (it says how many are marked on the stops instead) and notes on what each city's panel shows anyway (tap water, paying in cash, English); clicking a check opens its city at the tab it's about (a journey's check opens the journey). The assistant gets each stop's checks with it, fixes what it can when it plans and says what's left.
- **Map views**: **Route** (stops numbered by the trip day you arrive, or by the nights there with the legend's **Day | Nights** switch, and sized by the nights; elsewhere all stops are one size; lines coloured by travel mode, dashed where times are estimated from road distance; legend), **Weather** (fill = average high in ranges, e.g. 18–28°C, with the high written on each stop, or with **Low** in the legend the average low, on the same scale; hovering shows both; a ring around each stop fills with the share of rainy days), **Air** (five PM2.5 bands at the WHO's interim targets, 10/15/25/35 µg/m³, with the monthly average on each stop), **Cost** (one kind of cost at a time, picked in two rows, a group and then the kind in it: **Per day** on your daily cost choices; **Stay**: **Dorm bed** or **Private room** a night; **Food & drink**: **Local meal**, **Restaurant** dinner, **Café** coffee, **Bar** beer (0.5 L) or **Groceries** for a day; **Getting around**: local **Transport** a day, a **Taxi** ride of ~5 km, or a day of **Car rental** or **Scooter rental** (grey where that rental isn't usual); each group remembers the kind last picked in it; five bands of about a fifth of all cities each, in your currency; `kind=` in the address), **Mobile** (mobile internet in five bands by download speed, from slow under 25 Mbps to very fast 200+, with the speed on each stop), **Nearby** (roughly how many supermarkets, pharmacies, clinics & doctors or ATMs are within 1.5 km of the centre, picked with buttons like the month; coloured from none found to 50+), **Schengen** (the whole Schengen area in blue, the rest of the world left clear; stops inside or outside, and the 90/180 day counter) and **Visa** (every country in the world and its cities by the visa rule for the trip's passport, also those the app has no cities in yet (grey for the territories with no rule of their own): visa-free (also free movement and your own country), on arrival or ETA, e-visa, visa in advance, not admitted; the legend lists only the bands the passport meets and names it, and hovering shows the rule and how long you can stay). Weather and air show each place at the time of the trip by default (a stop in the month of its stay, other cities in the month you're at the nearest stop), or any month you pick. Each row of buttons over the map (the views, the months, the Nearby places, the cost groups and kinds) is one line that scrolls sideways when it doesn't fit, e.g. beside a city panel (the mouse wheel too, the edge fading where more is hidden), and the picked button stays in sight. The map's credits start folded into an ⓘ button that shows them. Outside the Route view the route is drawn plainly. Clicking a city anywhere (map, itinerary, timeline, another city) brings it into view if it's off screen or under the panel; panned away from the open city, its node (as on the map: circle, colour, number and ring) waits at the edge of the map towards it, with an arrow pointing at it and its name on a box, and a click brings it back; a click on a stop picks the stop, not the route line under it. A **location button** above the zoom buttons (they keep left of an open city or journey panel) moves the map to where you are, at the zoom it's at and to the middle of the part an open panel doesn't cover, and shows you as a dot (the browser asks to share your location the first time; with that refused, the button says *Location not available*).
- **City panel**, in tabs shown as icons (the open tab also has its name; the others name themselves on hover; on a narrow panel the bar scrolls sideways, and the mouse wheel scrolls it too), each section on its own card: **Overview** (description, suggested days per pace, one line per topic at a glance: a problem's line is red, and a line with one of the stop's warnings amber, saying why in a few words (*$35 (over bed budget)*, *feels like 2–10°C, ~12 rain days (colder than you like)*, *4h 45m from Shkodër (over your 3 h a day)*, with a Getting here line when the journey there has one); problems first, most serious first: visa needed, do-not-travel advice, foreign cards not working, then the warnings), **My visit** (your own, see above), **Transport** (in the city: public transport, how to pay, taxis, rentals; to other cities), **Weather** (the temperatures by month, high and low lines with each month's temperature by its dot (*24°*: highs above, lows below), and under them a chart of rain days by month; the next 10 days' forecast, fetched live from Open-Meteo (the last one fetched is kept on the device for a dozen cities, and shown from today on with *Offline: the forecast from Mon 12 Oct* when there's no connection; Today's forecast too), the same way: each day's sky, weekday and date (10/11) under its temperatures, and a chart of each day's rain in mm; the months of your stay highlighted, and today in the forecast; sunshine and air quality charts by month; temperatures as they feel or as measured, see below. Hover or tap a month or day for a tooltip above the chart (it never covers the chart): a month's humidity, rain days, hours of sunshine, or air quality; a day's sky and humidity, or its rain and chance of rain (the temperatures are by the dots). Feels like and Real share one temperature scale, so switching moves the lines, not the axis. The temperature charts have no High/Low legend: the lines' colours and labels say which is which), **Holidays** (the country's public holidays, from Google Calendar's public holiday calendars, a year at a time from 2021 to about five years ahead: **‹ 2027 ›** steps through the years, opening on the stay's year (else this year), and **Your stay** (a stop) or **Today** goes back to it; each day's date once, on its first line, the dates lined up (*Fri  1 Jan*, the weekday smaller and fainter); this year's past holidays faded, and a **Today** line on today; on a stop, **Arrive** and **Leave** lines on their days (arriving before the day's holidays, leaving after them) and the days between highlighted; a holiday of some states or provinces only says which under its name (*In Brandenburg, Mecklenburg-Western Pomerania, Saxony and 6 more*, tap for the rest), shown for the whole country since a city doesn't say which it's in; loaded when the tab first opens), **Costs** ($ icon), in three sub-tabs; on Daily cost and Prices a **USD | RSD** switch beside them shows their amounts in your currency or the city's own (one setting for every city; not shown where the city's currency is already yours) (**Daily cost**: one traveller's day item by item, bed, breakfast, lunch, dinner, café coffees, beers in a bar, public transport and taxi rides, from your preferences, with your daily budget and most per night beside Per day and Bed, *(budget $28)*, and over it the amount in red and the budget in red and bold (by how much on hover); change any item for this city and it's saved with the trip and counted in its total, a changed item has a reset icon next to its name, and **Reset all to preferences** undoes them all; **Prices**: Stay (dorm bed and private room), Food & drink: local meal, restaurant dinner, café coffee, beer in a bar and supermarket prices for 10 items: water, Coca-Cola, beer, bread, eggs, milk, pasta, bananas, tomatoes, chicken breast; hover the ⓘ by a meal, drink or Groceries for a day to see what each counts; price level vs a country you pick with a how-to-read explainer, Big Mac reference; **Paying & cash**: cards, contactless, cash, currency and ATMs). Every amount on Daily cost and Prices can be changed to the price you saw or paid there: click it, type it in the currency shown (Enter keeps it, Esc doesn't), and that city uses it from then on, in colour with a reset icon back to ours. A coffee, beer or taxi ride is typed per one, a DIY meal or groceries for a day as a whole, and **Per day** as what a day there really costs you (it then replaces the items' sum, which is still given). ## The trip assistant's tools

What the assistant can do, all through the app's own actions (`src/agent/schema.ts` describes them to the model,
`src/agent/tools.ts` runs them). Nothing re-fits or re-orders the trip by itself: the assistant decides the stops,
their order and nights. While planning (Plan with AI, Update plan) your setup stays as it is: the tools that change
it are refused, and the assistant suggests such changes instead.

| Tool | What it does | While planning |
|---|---|---|
| `get_trip` | The whole trip: settings, regions, every stop with dates and nights, the journeys between stops, cost and warnings | ✓ |
| `find_cities` | Cities the app has data for, with suggested days and tags; by country, tag or name | ✓ |
| `get_city_info` | One or more cities: a summary, or full sections (weather, costs, entry, safety, health, transport, daily life) | ✓ |
| `compare_cities` | A table of many cities (and the trip's stops) across chosen fields | ✓ |
| `get_route` | How to travel between two cities, or many pairs at once | ✓ |
| `get_shared_view` | The values on the parts of the screen you shared with your message | ✓ |
| `get_options` | The world's regions, countries, interests, passports, paces and budgets | ✓ |
| `get_visit` | My visit: stays, albums, links and notes per city or journey, with their ids, and prices the user saw (which the costs use) | ✓ |
| `save_visit_item`, `remove_visit_item` | Add a stay, album, link or note to My visit, change one (only the fields given) or remove one; also on a read-only trip | ✓ |
| `save_phrases` | Keep the user's own phrases, translated into each language they want (this country's, or every language on the trip, which it asks about), with how to say them; shown on the Phrases tab wherever the language is spoken | ✓ |
| `set_prices_seen` | Keep prices the user saw or paid in a city (from a receipt, a menu, a booking, or told), in the money paid, or set some back to the app's own: beds, meals, drinks, supermarket items, transport, a taxi ride, a whole day; the costs then use them for that city | ✓ |
| `set_itinerary` | The whole itinerary at once: every stop in order with its nights (a plan from scratch, a big rework) | ✓ (your locked stops stay) |
| `add_stop` | Add a city, after a given stop or where it fits the route, with its usual stay or given nights | ✓ |
| `remove_stop` | Remove a city (its nights are freed for the other stops) | ✓ |
| `set_nights` | A stop's nights; nothing else changes (locked only for nights you asked for) | ✓ |
| `move_stop` | Move one stop | ✓ |
| `reorder_stops` | A whole new order in one step, or reverse the trip | ✓ (reverses only the stops; not with **In this order**) |
| `update_settings` | Dates and how flexible they are, pace, travel style, interests, passport, number of stops, wishes… | Only to pick the dates within flexible ones |
| `update_preferences` | Your preferences from the Trip tab | ✗ |
| `add_region`, `update_region` | Add a region, set its days, or remove it | ✗ |
| `set_country_mode` | Must visit, optional or left out, and a country's days | ✗ |
| `set_locked` | Lock or unlock a stop | ✗ |
| `new_plan`, `switch_plan`, `rename_plan`, `delete_plan` | The trip's plans (versions of the itinerary) | ✗ |

## Other apps' assistants (MCP)

The Worker is an MCP server at `/mcp` (`worker/mcp.ts`) for other apps' AI assistants, with OAuth sign-in
(`worker/oauth.ts`): scope `trips:read`, and `trips:write` if the user leaves it ticked on the page where they allow
the app (an app allowed only to read isn't offered the tools that change trips). The tools (`src/agent/mcpTools.ts`)
are the assistant's own, each with an optional `trip` (an id or name; default: the trip opened last in the app), and
a few of its own:

| Tool | What it does |
|---|---|
| `list_trips` | The account's trips: id, name, dates, stops, and which is open in the app |
| `get_trip` | A trip in full: its description (dates, preferences, wishes, plans, where it is today), regions, stops, journeys, cost and checks |
| `find_cities`, `get_city_info`, `compare_cities`, `get_route`, `get_options` | As for the assistant (above) |
| `get_visit` | As for the assistant: My visit's stays, tickets, albums, links, notes and prices seen per city or journey, in the trip's order (one city if asked) |
| `get_journal` | The journal's days (the latest 60, or from and to given days) |
| `update_settings` … `reorder_stops` | The assistant's tools that change the trip (above), with `trips:write` |
| `save_visit_item`, `remove_visit_item`, `set_prices_seen`, `save_phrases` | The assistant's tools that change My visit, with `trips:write`: bookings (from the user's email, say) as stays and tickets; a booking saved again (the same reference or name, the same day) changes the one kept |
| `get_changes` | The changes apps made to the trip (the latest 30 of the last two weeks), with their ids |
| `undo` | Undoes the app's latest change, or a given one with every later one |

A change is saved at once (`worker/changes.ts`): the Account keeps the trip from before it, with the trip's `rev`
(counted up whenever its data changes) before and after; a change to My visit keeps the items it changed as they
were instead, and counts the `rev` up too. Undoing a change puts that trip (and those items) back, with every later
change still on, only while nothing else changed the trip, or those items, since (otherwise it would lose those
edits). Changes are
refused while the app's own assistant works on the trip; a read-only trip and the days already travelled stay as
they are, as for the assistant. The page sends the `rev` it has with each save, and a save from before another app's
change is refused (409 `changed`): the page then shows the trip as it is. It checks `/api/trips/:id/changes?since=REV`
when it comes into view and every 15 seconds, and lists those changes with Undo (`POST /api/trips/:id/changes/:change/undo`).

To connect: add `https://<site>/mcp` as a custom connector (Claude, ChatGPT), or
`claude mcp add --transport http rtw-map https://<site>/mcp`, `codex mcp add rtw-map --url https://<site>/mcp`,
`gemini mcp add --transport http rtw-map https://<site>/mcp`. Locally the address is `http://localhost:8787/mcp`
(the Worker of `npm run dev:api`, not the Vite server), with `npm run dev:runner` for the tools.

**Capitals from open data:** every country on the map without curated cities gets its capital from open data. All 202 such capitals then had their data drafted (2026-10-13; AI-drafted and not yet checked, as each seed file's source says): a profile (tags, popularity, days, cost factor, blurb), prices in the local currency (US dollars where official and street exchange rates differ widely: Iran, Syria, Lebanon, Yemen, Sudan, Myanmar, Turkmenistan, Bolivia, Burundi and others), routes to neighbours and hubs (overland where buses, trains or ferries run, else flights, noting a change), country notes, English level, religion, health, payments, local transport, shops and phrases (87 more languages), so they're planned like any curated city. A country added to the map later starts with open data only (nothing written for the app): GeoNames and Wikidata for the city and the country's basics, and the scripts above for weather, air, mobile internet, nearby places, travel advice, CDC health advice, population and price level. Nothing is made up for them: no prices (not even estimated from the price level, which is shown on its own), no connections or estimated bus rides, no tags, phrases, local transport, payments, shops or tap-water notes, and no English or card level. Plans never use them: the planner leaves their countries out, the assistant can't add them, and the city panel has no **+ Add to trip** and says only open data is there. (Their records carry placeholder popularity, days and cost factor only to fit the city type; nothing reads them.)

**Phrases read aloud:** 🔊 beside a phrase on the Phrases tab plays it (`src/ui/Speak.tsx`). Played again straight after, it's slower every second time (the 2nd, 4th, …: 0.5×, keeping its pitch), to catch each sound; another phrase starts again at normal speed. It's in the voice of whoever says the phrases (**Settings → Phrases → Said as**: a woman's or a man's), with their words. The app's seven phrases have clips made ahead of time by `npx tsx scripts/build-speech.ts [tags…]` (Azure AI Speech: a woman's and a man's plain neural voice per language, from the language's own country or one where it's spoken, a little slower than normal; all 74 languages Azure has have both); only new or changed phrases are read again, and old clips are removed. They're served at `/speech/<tag>/<key>.<hash>.mp3` (the Vite config serves `data/gen/speech/` while developing and copies it into the build): 1,036 clips, about 12 kB each. Your own phrases are read when first played, by `POST /api/speech` (signed in; 30 a minute; at most 100 characters) in the same language's voice. Each clip Azure reads is kept in an R2 bucket (`rtw-map-speech`, binding `SPEECH_CLIPS`) by its voice and text, so the same phrase asked for again, by anyone, comes from there instead of Azure. Each account gets 10 new phrases read by Azure a day; a phrase kept from before doesn't count, nor one Azure couldn't read. Played clips are kept on the device (Cache Storage, `phrase-speech`, `src/offline/phrases.ts`), so they play offline after that, and **Settings → Phrases** saves them beforehand, as the speaker set there says them: **The trip's languages** (with your own phrases in them, signed in; it stops, saying so, when the day's 10 are used up) or **Every language** (6.4 MB), with a progress bar, what's on the device and **Remove all**. Where Azure has no voice for a language, or a clip can't be fetched, the device's own voice reads it if it has one for the language; with neither, there's no 🔊. It needs an Azure Speech resource (here `rtw-map-speech` in resource group `rtw-map`, region `eastasia`, free F0 tier: 0.5 million characters a month, 20 requests a minute, which the script waits out): `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION` in `.env.local` for the script and local development, the key as a Worker secret (`npx wrangler secret put AZURE_SPEECH_KEY`) and the region in `wrangler.jsonc`.

To add a city: add a row to `data/seed/cities.csv` (and connections to `data/seed/connections.csv`), then run `npm run data:build`, then `npm run data:push`.

To review the seed data as tables, run `npm run dev` and open `/data.html` (development only, never deployed). Each seed file is a table you can sort, filter and search. It marks links to unknown cities or countries, repeated rows, values out of order (e.g. `daysMin` above `daysIdeal`) and countries or cities with no row. The pin by a column's name keeps it at the left while you scroll sideways (by default the line number and what the row is about, e.g. the country; remembered in this browser); click rows to highlight them, then **Only these** to compare just those (Esc clears). Money columns show the unit after their name; **Prices: As entered | All in …** switches the costs, route, taxi and rental prices to the display currency set in the app. It updates as you edit the files.

### Publishing

The site is published as static files on a Cloudflare Worker (`rtw-map`, configured in `wrangler.jsonc`) by `.github/workflows/deploy.yml`: on every push to `main`, by hand, and after the weekly data refresh. It pulls the data from R2, runs the tests, builds and runs `wrangler deploy`. Repository secrets: the four `R2_*` settings, `CLOUDFLARE_API_TOKEN` (permissions: Workers Scripts Edit, Account Settings Read, User Details Read, Memberships Read) and `CLOUDFLARE_ACCOUNT_ID`.

The Worker also serves the API (`worker/`): `/api/session`, `/api/auth/google`, `/api/auth/logout`, `/api/trips` (list, create, open, save, delete the user's trips), `/api/chat`, which forwards the assistant conversation to Gemini, `/api/admin/limits` (admins: other daily limits per email), `/api/connections` (the apps allowed to read or change the trips), `/api/trips/:id/changes` (their changes, and undo), `/api/phrases` (the user's own phrases, for every trip), `/api/push` (notifications when the assistant finishes), and `/mcp` with `/oauth/…` and `/.well-known/oauth-…` for other apps' assistants (above; `run_worker_first` in `wrangler.jsonc` sends those paths to the Worker). The MCP tools that need the city data run on the runner (`POST /tool`, with `RUNNER_SECRET`); without a runner only `list_trips` works. Per-user data (trips and assistant usage) lives in one Durable Object per Google account (`Account`, SQLite); the admin list of limits in a `_settings` instance of it. Secrets, set once with `npx wrangler secret put <name>`: `GEMINI_API_KEY`, `SESSION_SECRET` (random; signs the session cookie), `ADMIN_EMAILS` (comma-separated; who may edit the limits) `AZURE_SPEECH_KEY` (reads the user's phrases aloud, `/api/speech`) and `VAPID_PRIVATE_KEY` (signs the notifications when the assistant finishes; below). In `wrangler.jsonc`: `GEMINI_MODEL`, `GOOGLE_CLIENT_ID` (the OAuth client for Sign in with Google; its authorised JavaScript origins are the site and `http://localhost:5317`), the `Account` Durable Object, `AZURE_SPEECH_REGION`, the `rtw-map-speech` R2 bucket (`SPEECH_CLIPS`, the user's phrases read aloud, created once with `npx wrangler r2 bucket create rtw-map-speech`), and the per-minute rate limits (assistant calls, trip saves, phrases read aloud). For local development, put `GEMINI_API_KEY` and `SESSION_SECRET` in `.env.local`.

A message to the assistant about a trip saved to the account is answered on the server, so it finishes even when the page is closed or the phone loses its connection: `POST /api/runs` saves the trip and chat as on screen and hands the run to the runner (`runner/`, a Node service on Google Cloud Run), which queues it on Cloud Tasks; Cloud Tasks calls the runner back and holds that request open while the run goes (Cloud Run gives a request CPU only while it's open, for up to 30 minutes). The runner runs the same loop and tools as the browser (`src/agent/engine.ts`) on its own copy of the trip, calls the model through the Worker (`/internal/runs/…`, with `RUNNER_SECRET`: same allowance and cost tracking as `/api/chat`), and saves the trip and the reply after each step. The page follows the run (`GET /api/runs/:id`, with the trip when it changed), shows its changes as they land, picks it up again when the trip is opened, and stops it (`POST /api/runs/:id/stop`: the runner hears it after the step under way, or within 5 seconds while it waits to retry); the trip can't be saved from the page meanwhile. A run not heard of for 5 minutes is marked failed. Without a runner (`RUNNER_URL` unset) the browser answers itself, as before. When a run ends (not stopped), the user hears of it even with the app closed: while the assistant works, **Notify me when it's done** (*Notify my phone…* on a phone; shown until the browser has asked) asks for the browser's permission and signs that browser up for Web Push (`src/agent/notify.ts`: `PUT /api/push` keeps its subscription with the account, the last 10 browsers; only the browsers' own push services). At the run's end the Worker sends each of them *The assistant replied · trip* with the reply's first line, or *couldn't finish* with the error (`worker/push.ts`: encrypted for that browser, RFC 8291, and signed with the site's VAPID key, RFC 8292; a browser that's gone is forgotten); the service worker shows it unless the app is in front, and a click opens that trip's chat (`pwa/sw.ts`). The page, while open and not in front, also puts it in the tab's title. On an iPhone or iPad it works only for the app added to the Home Screen (iOS 16.4+), not in a Safari tab. Keys, once: `npx tsx scripts/vapid-keys.ts` puts the private key in `.env.local` and prints the public one for `VAPID_PUBLIC_KEY` in `wrangler.jsonc`; then `grep '^VAPID_PRIVATE_KEY=' .env.local | cut -d= -f2- | npx wrangler secret put VAPID_PRIVATE_KEY`. Setup, once: `scripts/gcp-setup.sh <project-id>` (APIs, the image repository, the runner's service account and queue, and a deployer that GitHub Actions uses with Workload Identity Federation); then the repository variables it prints and the `RUNNER_SECRET` secret, the same value as the Worker's (`npx wrangler secret put RUNNER_SECRET`), and `RUNNER_URL` (the Cloud Run service's address) in `wrangler.jsonc`. The Deploy workflow builds the runner (`npm run build:runner`), pushes its image and deploys it.

### Data storage

The `data/` folder is kept in a private **Cloudflare R2** bucket instead of git, synced by `scripts/r2.ts`:

| Command | What it does |
|---|---|
| `npm run data:pull` | Download the data from R2 into `data/` (only changed files) |
| `npm run data:push` | Upload new or changed files. When any seed file changed, the whole `data/seed/` folder is also saved as a dated copy (`snapshots/<date>/seed/`, one per day) |
| `npm run data:snapshots` | List the dated copies of the seed data |
| `npm run data:restore -- <date>` | Put that day's seed copy back into `data/seed/`; check it, then `data:push` to make it current |

Seed data is hand-made and can't be rebuilt, so it gets dated copies; generated data is rebuilt by the scripts.

Files go up and down 16 at a time (a full pull of the thousand-odd files takes about 15 s). The GitHub workflows keep `data/` between runs (`actions/cache`, restoring the newest copy from any run), so their pull downloads only what changed in R2 since; R2 stays the source of truth.

Setup (once):
1. In the Cloudflare dashboard, create an R2 bucket (private, the default).
2. Create an R2 API token with **Object Read & Write** on that bucket. Note the Access Key ID, the Secret Access Key and your Account ID.
3. Put them in `.env.local` (git-ignored):
   ```
   R2_ACCOUNT_ID=…
   R2_ACCESS_KEY_ID=…
   R2_SECRET_ACCESS_KEY=…
   R2_BUCKET=…
   ```
4. Add the same four values as GitHub repository secrets, for the weekly refresh workflow (pull → refresh → test → push).

**Estimates:** costs, connections, English levels, local transport, taxi, rental, health (tap water, risks, healthcare; vaccines only where CDC data is missing), shopping and payment data are hand-made seed estimates and are labelled as such in the UI. Visa and safety information always links to official sources; verify before travelling.
